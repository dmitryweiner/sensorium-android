# Sensorium — план разработки

Android-приложение для сбора, анализа и поиска аномалий в сигналах датчиков устройства.
Первая цель — магнитные аномалии; архитектура закладывается под расширение на другие сигналы
(Wi-Fi, BLE, сотовая сеть, GNSS, барометр, звук и т.д.).

- **Ядро** (платформенно-независимая логика, хранение, анализ) — Rust, без зависимостей
  от Android, чтобы позже портировать на iOS, десктоп и CLI.
- **Интерфейс и доступ к датчикам** — Kotlin (Jetpack Compose).
- **Лицензия** — GPL-3.0 (уже в репозитории). Все зависимости совместимы с GPL и с
  требованиями **F-Droid**: никаких Google Play Services и проприетарных SDK.
- **Сборка и релизы** — GitHub Actions (раздел 5.1).
- **Первичная цель поиска** — подземные коммуникации и металл (трубы, кабели, арматура, люки).
- **Тестовое устройство** — Xiaomi Redmi Note 12 Pro 5G (Android 13+, MIUI/HyperOS).

Все решения, согласованные с владельцем проекта, собраны в разделе 8.

## 1. Пользовательский сценарий (MVP)

1. Пользователь открывает приложение, выбирает или создаёт **район** (area) и нажимает
   **«Начать запись»**.
2. Приложение в фоне (foreground service с уведомлением) пишет показания магнитометра,
   акселерометра, гироскопа/вектора вращения и координаты GNSS. Пользователь ходит по району.
3. Пользователь нажимает **«Остановить»**. Сессия сохраняется локально и привязывается к району.
4. Пользователь открывает район, видит все его сессии (проходы), отмечает нужные и нажимает
   **«Анализировать»**. Анализ идёт по всем отмеченным сессиям сразу — **многопроходное
   накопление**: чем больше проходов, тем плотнее и надёжнее карта.
5. Ядро строит сетку по территории, считает оценку аномальности каждой ячейки и
   возвращает результат. Приложение показывает **тепловую карту** поверх карты местности
   и треки проходов. Тап по ячейке — детали: медиана поля, отклонение от базовой линии,
   градиент, число измерений и проходов, доверие.
6. Результат можно экспортировать (GeoJSON, CSV) и поделиться.

Не в MVP: облачная синхронизация, аккаунты, совместные карты, фоновый сбор без уведомления,
офлайн-загрузка тайлов региона (только кэш просмотренных тайлов MapLibre), русская локализация.

### 2.1. Разделение ответственности

**Kotlin отвечает за** всё платформенно-специфичное:
- доступ к датчикам (`SensorManager`) и геолокации (`LocationManager`);
- foreground service, разрешения, уведомления, жизненный цикл;
- UI, карта, отрисовка тепловой карты, экспорт через share-intent;
- передача сырых отсчётов в ядро пачками (batch) — не по одному через FFI.

**Rust отвечает за** всё, что должно пережить смену платформы:
- доменная модель (район, сессия, поток сигнала, отсчёт, геофикс);
- хранение (SQLite через `rusqlite` с feature `bundled`) — один формат данных на всех платформах;
- препроцессинг: синхронизация по времени, интерполяция координат к отсчётам датчика,
  фильтрация, перевод в мировую систему координат;
- детекторы аномалий, согласование сессий и агрегация в географическую сетку;
- сериализация результата (GeoJSON, CSV) и описание «что такое аномалия» для UI.

Правило: **в ядре нет ни одной строки, зависящей от Android**. Всё, что нужно ядру от платформы,
приходит через вызовы API (данные) или абстракции (путь к БД, часы).

### 2.2. FFI: UniFFI

Используем [UniFFI](https://mozilla.github.io/uniffi-rs/) (Mozilla): из Rust-интерфейса
генерируются Kotlin-биндинги сейчас и Swift-биндинги для iOS в будущем. Ручной JNI не пишем.

Принципы интерфейса:
- API «толстыми» вызовами: `push_samples(batch)`, `analyze(area_id, session_ids, params)
  -> AnalysisResult`, а не per-sample.
- Долгие операции (анализ) — синхронные в Rust, вызываются из Kotlin на `Dispatchers.Default`;
  прогресс — через callback-интерфейс UniFFI.
- Все экспортируемые типы — простые записи (records) и enum, без ссылок на внутренности ядра.
- Сборка: `cargo-ndk` для `arm64-v8a`, `armeabi-v7a`, `x86_64`; Gradle-задача запускает
  `cargo ndk` и `uniffi-bindgen`, кладёт `.so` в `jniLibs` и Kotlin в `build/generated`.

### 2.3. Модель данных

```
Area
  id, name, created_at, notes          — район; группирует сессии для многопроходного анализа
Session
  id, area_id, started_at, finished_at, status (finished | aborted),
  device_info, app_version, notes
SignalStream (в рамках сессии)
  kind: Magnetometer | MagnetometerUncalibrated | Accelerometer | Gyroscope |
        RotationVector | Barometer | ... (расширяемый enum)
  sample_rate_hz (номинальная)
Sample
  stream_id, t_mono_ns (монотонное время датчика), values[0..n], accuracy_flag
LocationFix
  session_id, t_mono_ns, t_wall_ms, lat, lon, alt, h_accuracy_m, speed, bearing, provider
AnalysisRun
  id, area_id, session_ids[], detector, params_json, algo_version, created_at,
  result_blob (сетка)
```

Многопроходность заложена в схему с первого дня: сессия всегда принадлежит району,
анализ принимает набор сессий, результат хранит, какие сессии и какая версия алгоритма
в него вошли.

Время: везде **монотонное время** (`SensorEvent.timestamp`, `Location.elapsedRealtimeNanos`),
стенные часы хранятся только для отображения. Это снимает проблемы с переводом часов и NTP.

Объёмы: магнитометр 50 Гц × 3 float × 1 ч ≈ 180 тыс. отсчётов, ≈ 4–5 МБ на сессию
с остальными датчиками — приемлемо для SQLite на устройстве.

### 2.4. Хранение

SQLite внутри ядра (`rusqlite`, `bundled`). Файл БД — в `filesDir` приложения, путь передаётся
в ядро при инициализации. Запись отсчётов — транзакциями по пачкам (~1 с данных), чтобы
не терять батарею на fsync. Миграции схемы — внутри ядра (нумерованные SQL-скрипты).

Альтернатива (Room на стороне Kotlin) отвергнута: пришлось бы дублировать хранение при портировании.

## 3. Анализ магнитных аномалий

### 3.1. Физика и источники шума

- Магнитное поле Земли на поверхности ≈ 25–65 мкТл, медленно меняется в пространстве.
  Локальные аномалии: железобетон, трубы, рельсы, автомобили, ЛЭП, крупные металлические
  объекты, геологические структуры.
- Магнитометр телефона: шум ≈ 0.1–1 мкТл, смещение от собственных компонентов (hard iron),
  искажения (soft iron). Android выдаёт калиброванное поле (`TYPE_MAGNETIC_FIELD`) и
  некалиброванное с оценкой смещения (`TYPE_MAGNETIC_FIELD_UNCALIBRATED`). Пишем **оба**.
- Показания в системе координат устройства зависят от ориентации телефона. Поэтому:
  - MVP работает с **модулем вектора |B|** — он от ориентации не зависит;
  - затем, используя `TYPE_ROTATION_VECTOR`, переводим в мировую систему (ENU) и получаем
    вертикальную компоненту и наклонение — более информативные признаки.
- Ложные срабатывания: сам пользователь (ключи, часы, вторая техника), проезжающие машины,
  пересчёт калибровки системой (скачок смещения), низкая точность GNSS.

### 3.2. Специфика цели: подземные коммуникации и металл

Трубы, кабели, арматура и люки дают **компактные** аномалии масштаба 1–5 м с резким
градиентом. Следствия для алгоритма и UX:
- сетка по умолчанию **3 м** (диапазон 2–5 м), то есть мельче типичной точности GNSS;
  компенсируем взвешиванием по точности фикса и накоплением по нескольким проходам;
- наряду с |B| ключевой признак — **градиент вдоль трека** d|B|/ds: он не зависит от
  медленного дрейфа базовой линии и хорошо выделяет линейные объекты (трубы, кабели);
- повторяемость: аномалия, подтверждённая в двух и более проходах, получает бонус
  к доверию, одиночная — штраф;
- подсказки пользователю на экране записи: идти медленно (≤ 1.5 м/с), держать телефон
  стабильно и низко, не менять ориентацию резко, не носить металл в карманах;
- геологические и крупные инфраструктурные аномалии не приоритет, но параметры
  (размер ячейки, чувствительность, сглаживание) остаются настраиваемыми.

### 3.3. Пайплайн анализа (в Rust)

1. **Загрузка и очистка**: отбросить отсчёты с `accuracy == UNRELIABLE`, фиксы с
   `h_accuracy > порог` (по умолчанию 25 м), участки без координат.
2. **Геопривязка**: каждому отсчёту датчика — координата линейной интерполяцией между
   соседними фиксами по монотонному времени.
3. **Признаки**: |B| и градиент вдоль трека d|B|/ds (оба в MVP); позже — компоненты
   в ENU, вертикальная составляющая.
4. **Детекция скачков калибровки**: резкие ступени |B| при неизменном некалиброванном
   сигнале → разбить сессию на сегменты с отдельной базовой линией.
5. **Базовая линия**: робастная (медиана + MAD) по сегменту **каждой сессии отдельно**;
   опционально — ожидаемое поле из модели **WMM/IGRF** для широты/долготы/даты
   (crate `world_magnetic_model` или своя реализация), что даёт абсолютную аномалию.
6. **Согласование сессий**: перед слиянием признаки каждой сессии приводятся к общей
   базовой линии (вычитание смещения сессии/сегмента), иначе разная калибровка
   магнитометра в разные дни даст ложные «ступени» между проходами.
7. **Сетка**: ячейки 3 м по умолчанию (настраиваемо 2–50 м) в локальной проекции
   (UTM/равнопромежуточной вокруг центра района). В ячейке: n, число проходов (сессий),
   медиана, MAD, min/max каждого признака.
8. **Оценка аномальности** ячейки: робастный z-score медианы относительно базовой линии
   и нормированный градиент, объединённые в один score; умножается на доверие от n,
   числа проходов и точности GNSS. Отдельно помечаем ячейки с высокой внутренней
   дисперсией (нестационарное поле — например, движущийся источник).
9. **Пространственное сглаживание** (опционально): медианный фильтр по соседям, чтобы
   убрать одиночные выбросы.
10. **Результат**: список ячеек (центр, полигон, score, доверие, статистики), треки,
    сводка (базовые линии, число сегментов, доля отброшенных данных), версия алгоритма
    и параметры. Сохраняется как `AnalysisRun`.

### 3.4. Расширяемость на другие сигналы

В ядре — два трейта:

```rust
trait FeatureExtractor { fn extract(&self, session: &Session) -> FeatureSeries; }
trait AnomalyDetector   { fn detect(&self, features: &[FeatureSeries], params: &Params) -> GridResult; }
```

Магнитный детектор — первая реализация. Дальше по тому же контракту: Wi-Fi RSSI
(«дыры» и необычно сильные источники), BLE-маячки, уровень сотового сигнала, GNSS
(С/N0, многолучёвость — косвенный признак экранирования), барометр (микрорельеф),
уровень шума. Реестр детекторов отдаёт UI список доступных «слоёв» для карты.

### 3.5. Тестирование алгоритмов

- Синтетические сессии: ровное поле + шум + внедрённый магнитный диполь (точечный объект)
  и линейный источник (труба) на известных позициях → детектор обязан найти их с заданной
  точностью. Проверяем и отсутствие ложных срабатываний на чистых данных, и то, что слияние
  двух сессий с разным смещением калибровки не порождает ступеней.
- Регрессионные «золотые» дампы с реальных прогулок на Redmi Note 12 Pro 5G
  (хранить в `core/testdata`, небольшие). Характеристики его магнитометра (шум, частота,
  поведение калибровки) замеряем на M1 и фиксируем в `docs/devices.md`.
- Property-тесты (`proptest`) на инвариантность к ориентации устройства для |B|.
- CLI `sensorium-cli analyze dump.sqlite --out result.geojson` — быстрая итерация без телефона.

## 4. Android-приложение

### 4.1. Стек

- Kotlin 2.x, Jetpack Compose, Material 3, одна Activity, Navigation Compose.
- Архитектура MVVM + однонаправленный поток данных; корутины и Flow.
- DI — Hilt (или ручной, если модулей мало; решить на M1).
- minSdk 26, targetSdk — актуальный (35+).
- Локализация: интерфейс на **английском**, все строки в ресурсах; русский добавляется
  отдельным шагом (M3).
- Карта — **MapLibre Native Android** с OSM-растровыми или векторными тайлами
  (открытая лицензия, есть встроенные `HeatmapLayer`/`FillLayer`, стиль через JSON).
  Офлайн-регионы не в MVP; используется штатный кэш тайлов MapLibre.
- Геолокация — платформенный `LocationManager` (провайдер GNSS), без Play Services.
- **F-Droid — обязательная цель**: никаких проприетарных зависимостей, сборка из исходников
  воспроизводимой командой, `fastlane/metadata` с описанием и скриншотами, версии
  Rust/NDK зафиксированы в репозитории (`rust-toolchain.toml`, `ndkVersion` в Gradle).

### 4.2. Сбор данных

- `RecordingService` — foreground service типа `location` (Android 14+ требует явный тип),
  постоянное уведомление с таймером и кнопкой «Стоп».
- Частоты по умолчанию: магнитометр 50 Гц, акселерометр/вектор вращения 50 Гц,
  гироскоп 50 Гц, GNSS 1 Гц. Используем `maxReportLatencyUs` для батчинга датчиков
  и `WakeLock` PARTIAL на время записи.
- Отсчёты накапливаются в кольцевом буфере и сбрасываются в ядро пачками раз в ~1 с.
- Переживание смерти процесса: ядро коммитит транзакции часто; при рестарте сервиса
  сессия закрывается как «прервана» (`aborted`), записанные данные не теряются.
- **MIUI/HyperOS** (тестовый Redmi Note 12 Pro 5G) агрессивно убивает фоновые сервисы:
  при первом запуске показываем инструкцию отключить оптимизацию батареи и разрешить
  автозапуск для приложения; проверяем живучесть сервиса на часовой записи в M1.
- Разрешения: `ACCESS_FINE_LOCATION`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`,
  `POST_NOTIFICATIONS`. `ACCESS_BACKGROUND_LOCATION` не нужен (есть видимое уведомление).

### 4.3. Экраны

1. **Главный / запись**: выбор района, кнопка Старт/Стоп, живые показания |B| (график
   последних 30 с), статус GNSS (точность, число спутников), счётчик отсчётов, индикатор
   качества калибровки магнитометра с подсказкой «покрутите телефон восьмёркой»,
   подсказка по скорости ходьбы.
2. **Районы**: список районов с числом сессий и датой последнего прохода; создание,
   переименование, удаление.
3. **Район**: карта со всеми треками, список сессий с чекбоксами (какие включать в анализ),
   кнопка «Анализировать», выбор детектора и параметров (размер ячейки, чувствительность),
   экспорт/удаление. Отдельная сессия открывается для просмотра трека, заметок и удаления.
4. **Результат**: тепловая карта + треки, легенда, слайдер порога, тап по ячейке → детали,
   переключение слоёв (разные детекторы), экспорт GeoJSON/CSV/PNG-снимок.
5. **Настройки**: частоты датчиков, единицы, источник тайлов, размер кэша тайлов,
   удаление данных.

### 4.4. Приватность

Все данные остаются на устройстве. Треки GNSS — чувствительные данные: экспорт только по
явному действию пользователя, в настройках — удаление всех данных одной кнопкой. Без
аналитики и сетевых запросов, кроме загрузки тайлов карты (отключаемо, кэш).

```
└── .github/
    ├── dependabot.yml
    └── workflows/               # ci.yml, release.yml
```

### 5.1. Сборка и релизы в GitHub Actions

Вся сборка идёт через GitHub Actions; локальная сборка повторяет те же команды,
а CI служит эталоном «как собирать».

**`ci.yml` — на каждый push и pull request:**
1. Job `rust`: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
   `cargo test` на хосте (Linux). Кэш `~/.cargo` и `target/`.
2. Job `android`: установка NDK фиксированной версии, `rustup target add` для
   `aarch64-linux-android`, `armv7-linux-androideabi`, `x86_64-linux-android`,
   `cargo ndk` сборка `.so`, генерация Kotlin-биндингов UniFFI, затем
   `./gradlew lint testDebugUnitTest assembleDebug`. Кэш Gradle.
3. Debug APK загружается как **артефакт workflow** (хранение 14 дней), чтобы любой
   коммит можно было поставить на телефон без локальной сборки.
4. Проверка, что сгенерированные биндинги совпадают с закоммиченным интерфейсом
   (если биндинги хранятся в репозитории), иначе падение.

**`release.yml` — на тег `v*`:**
1. Те же проверки, что в `ci.yml`.
2. Сборка `assembleRelease`, подпись APK ключом из GitHub Secrets
   (`SIGNING_KEYSTORE_BASE64`, `SIGNING_KEY_ALIAS`, `SIGNING_STORE_PASSWORD`,
   `SIGNING_KEY_PASSWORD`). `versionName` берётся из тега, `versionCode` — монотонный.
3. Создание **GitHub Release** с подписанными APK (per-ABI и universal), changelog
   из коммитов и контрольными суммами SHA-256.
4. Для F-Droid ничего отдельно не собираем: F-Droid строит из исходников по своему
   рецепту (`metadata/<package>.yml` в их репозитории), который ссылается на тот же тег.
   Поэтому сборка должна быть детерминированной и без сетевых шагов, кроме загрузки
   зависимостей. Воспроизводимость (идентичный APK у F-Droid и в GitHub Release) — цель M5.

**Прочее:**
- `dependabot.yml` для Cargo, Gradle и GitHub Actions.
- Все версии инструментов зафиксированы: `rust-toolchain.toml`, `ndkVersion`,
  Gradle wrapper, версии actions по SHA.
- Ветка `main` защищена: слияние только при зелёном `ci.yml`.

## 6. Этапы

### M0 — Скелет (≈ 1 неделя)
- Rust workspace, пустое ядро, UniFFI-функция `version()`.
- Android-проект, Gradle-плагин сборки Rust, вызов `version()` на экране.
- `ci.yml` зелёный, debug APK скачивается из артефактов workflow; каркас `release.yml`.
- README с инструкцией сборки.
- **Готово, когда**: свежий клон собирается одной командой, CI публикует APK,
  приложение показывает версию ядра на Redmi Note 12 Pro 5G.

### M1 — Сбор данных (≈ 2 недели)
- Схема БД и API ядра: районы и сессии (`create_area`, `create_session`, `push_samples`,
  `push_locations`, `finish_session`, `list_*`, `delete_*`).
- `RecordingService`, разрешения, уведомление, экран записи с живым графиком |B|,
  подсказки по MIUI.
- Экраны районов и района с треками на карте (MapLibre, кэш тайлов).
- CLI: экспорт сессии в CSV. Замер характеристик магнитометра тестового телефона
  (`docs/devices.md`).
- **Готово, когда**: часовая прогулка записывается без потерь, сервис не убит MIUI,
  просадка батареи не больше ~8 %/ч.

### M2 — Магнитный анализ и тепловая карта (≈ 3 недели)
- Пайплайн из п. 3.3 на |B| и градиенте: шаги 1–3, 5 (относительная базовая линия),
  6 (согласование сессий), 7–10. Многопроходное накопление по району с первого релиза.
- Синтетические тесты с диполем и линейным источником, тест слияния сессий, CLI `analyze`.
- Экран результата: тепловая карта, легенда, детали ячейки, порог, выбор сессий.
- Экспорт GeoJSON/CSV.
- Первый релиз `v0.1.0` через `release.yml`.
- **Готово, когда**: известный люк/труба на тестовом маршруте выделяется на карте после
  двух-трёх проходов, а чистый маршрут — почти не окрашен.

### M3 — Качество измерений (≈ 2–3 недели)
- Детекция скачков калибровки и сегментация (шаг 4).
- Перевод в ENU через вектор вращения; вертикальная компонента.
- Базовая линия по WMM/IGRF — абсолютные аномалии.
- Фильтр по скорости (в транспорте не считаем), индикатор качества калибровки на записи.
- Повторяемость аномалии между проходами как отдельный признак доверия.
- Русская локализация интерфейса.

### M4 — Расширение на другие сигналы (≈ 3–4 недели)
- Трейты `FeatureExtractor`/`AnomalyDetector`, реестр детекторов, слои на карте.
- Wi-Fi RSSI и BLE-сканы (с учётом троттлинга сканирования в Android), уровень сотового
  сигнала, барометр, GNSS C/N0.
- Общие параметры детекторов в UI, пресеты.

### M5 — Портирование и зрелость (по мере необходимости)
- Swift-биндинги UniFFI, прототип на iOS.
- Десктопное приложение/веб-визуализация результатов CLI.
- Публикация в F-Droid (рецепт сборки, воспроизводимый APK); опционально Google Play.

## 7. Риски

| Риск | Смягчение |
|---|---|
| Калибровка магнитометра Android «прыгает» посреди сессии | Писать и некалиброванный сигнал; сегментация по скачкам; собственная оценка смещения |
| Разная калибровка между сессиями ломает многопроходное слияние | Согласование базовых линий (шаг 6); тест на синтетике; градиент не зависит от смещения |
| Ориентация телефона маскирует/создаёт аномалии | MVP на \|B\|; далее ENU через вектор вращения; проверка инвариантности тестами |
| Ячейка 3 м мельче точности GNSS (10–30 м в городе) | Взвешивание по `h_accuracy`; накопление проходов; градиент вдоль трека как основной признак; размер ячейки регулируется |
| Сам пользователь — источник помех | Подсказки в UI (убрать металл из карманов, держать стабильно); детекция периодичности шагов |
| MIUI/HyperOS убивает сервис записи | Инструкция по отключению оптимизации батареи и автозапуску; проверка живучести в M1; сессия со статусом «прервана» сохраняет данные |
| Сложность сборки Rust ↔ Android отпугнёт контрибьюторов | Gradle-плагин делает всё сам; `rust-toolchain.toml`; инструкция в README; CI как эталон |
| Ограничения фоновых сервисов и батарея | Foreground service, батчинг датчиков, WakeLock только на запись, замеры на M1 |
| Привязка к картографическому SDK | Карта изолирована за интерфейсом `MapRenderer`; данные — нейтральный GeoJSON |
| Один тестовый телефон — выводы могут не переноситься на другие | CLI и синтетика не зависят от устройства; `docs/devices.md` для накопления данных по другим моделям |

## 8. Принятые решения

Согласовано с владельцем проекта 2026-10-11.

| Вопрос | Решение |
|---|---|
| FFI | UniFFI (Kotlin сейчас, Swift потом), без ручного JNI |
| Хранение | В ядре на Rust, SQLite через `rusqlite` (`bundled`); Kotlin без своей БД |
| Карта | MapLibre Native Android + OSM-тайлы; офлайн-регионы не в MVP, только кэш |
| Геолокация | Платформенный `LocationManager`, без Play Services |
| Распространение | F-Droid обязателен; релизы также как APK в GitHub Releases |
| Сборка | GitHub Actions: проверки и debug APK на каждый push, подписанный релиз по тегу `v*` |
| minSdk | 26 |
| Язык интерфейса | Английский в первом релизе, русский в M3 |
| Многопроходные карты | С самого начала (M2): сессии группируются в районы, анализ по набору сессий |
| Цель поиска | Подземные коммуникации и металл: сетка 3 м по умолчанию, градиент вдоль трека как ключевой признак |
| Тестовое устройство | Xiaomi Redmi Note 12 Pro 5G, Android 13+ |
| Единицы | Микротесла (мкТл) |
| Язык кода | Код, комментарии, коммиты — английский; документация пока на русском |

Открытых вопросов, блокирующих старт M0, нет.
