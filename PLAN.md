# Sensorium — план разработки

Android-приложение для сбора, анализа и поиска аномалий в сигналах датчиков устройства.
Первая цель — магнитные аномалии; архитектура закладывается под расширение на другие сигналы
(Wi-Fi, BLE, сотовая сеть, GNSS, барометр, звук и т.д.).

- **Ядро** (сбор-независимая логика, хранение, анализ) — Rust, без зависимостей от Android,
  чтобы позже портировать на iOS, десктоп и CLI.
- **Интерфейс и доступ к датчикам** — Kotlin (Jetpack Compose).
- **Лицензия** — GPL-3.0 (уже в репозитории). Все зависимости выбираем совместимыми,
  предпочитая открытые решения без привязки к Google Play Services.

---

## 1. Пользовательский сценарий (MVP)

1. Пользователь открывает приложение, нажимает **«Начать запись»**.
2. Приложение в фоне (foreground service с уведомлением) пишет показания магнитометра,
   акселерометра, гироскопа/вектора вращения и координаты GNSS. Пользователь ходит по району.
3. Пользователь нажимает **«Остановить»**. Сессия сохраняется локально.
4. В списке сессий пользователь выбирает сессию и нажимает **«Анализировать»**.
5. Ядро строит сетку по территории, считает оценку аномальности каждой ячейки и
   возвращает результат. Приложение показывает **тепловую карту** поверх карты местности
   и трек прохода. Тап по ячейке — детали: медиана поля, отклонение от базовой линии,
   число измерений, доверие.
6. Результат можно экспортировать (GeoJSON, CSV) и поделиться.

Не в MVP: облачная синхронизация, аккаунты, совместные карты, фоновый сбор без уведомления.

### 2.1. Разделение ответственности

**Kotlin отвечает за** всё платформенно-специфичное:
- доступ к датчикам (`SensorManager`) и геолокации (`LocationManager`);
- foreground service, разрешения, уведомления, жизненный цикл;
- UI, карта, отрисовка тепловой карты, экспорт через share-intent;
- передача сырых отсчётов в ядро пачками (batch) — не по одному через FFI.

**Rust отвечает за** всё, что должно пережить смену платформы:
- доменная модель (сессия, поток сигнала, отсчёт, геофикс);
- хранение сессий (SQLite через `rusqlite` с feature `bundled`) — один формат данных на всех платформах;
- препроцессинг: синхронизация по времени, интерполяция координат к отсчётам датчика,
  фильтрация, перевод в мировую систему координат;
- детекторы аномалий и агрегация в географическую сетку;
- сериализация результата (GeoJSON, CSV) и описание «что такое аномалия» для UI.

Правило: **в ядре нет ни одной строки, зависящей от Android**. Всё, что нужно ядру от платформы,
приходит через вызовы API (данные) или абстракции (путь к БД, часы).

### 2.2. FFI: UniFFI

Используем [UniFFI](https://mozilla.github.io/uniffi-rs/) (Mozilla): из Rust-интерфейса
генерируются Kotlin-биндинги сейчас и Swift-биндинги для iOS в будущем. Ручной JNI не пишем.

Принципы интерфейса:
- API «толстыми» вызовами: `push_samples(batch)`, `analyze(session_id, params) -> AnalysisResult`,
  а не per-sample.
- Долгие операции (анализ) — синхронные в Rust, вызываются из Kotlin на `Dispatchers.Default`;
  прогресс — через callback-интерфейс UniFFI.
- Все экспортируемые типы — простые записи (records) и enum, без ссылок на внутренности ядра.
- Сборка: `cargo-ndk` для `arm64-v8a`, `armeabi-v7a`, `x86_64`; Gradle-задача запускает
  `cargo ndk` и `uniffi-bindgen`, кладёт `.so` в `jniLibs` и Kotlin в `build/generated`.

### 2.3. Модель данных

```
Session
  id, started_at, finished_at, device_info, app_version, notes
SignalStream (в рамках сессии)
  kind: Magnetometer | MagnetometerUncalibrated | Accelerometer | Gyroscope |
        RotationVector | Barometer | ... (расширяемый enum)
  sample_rate_hz (номинальная)
Sample
  stream_id, t_mono_ns (монотонное время датчика), values[0..n], accuracy_flag
LocationFix
  session_id, t_mono_ns, t_wall_ms, lat, lon, alt, h_accuracy_m, speed, bearing, provider
AnalysisRun
  id, session_id, detector, params_json, created_at, result_blob (сетка)
```

Время: везде **монотонное время** (`SensorEvent.timestamp`, `Location.elapsedRealtimeNanos`),
стенные часы хранятся только для отображения. Это снимает проблемы с переводом часов и NTP.

Объёмы: магнитометр 50 Гц × 3 float × 1 ч ≈ 180 тыс. отсчётов, ≈ 4–5 МБ на сессию
с остальными датчиками — приемлемо для SQLite на устройстве.

### 2.4. Хранение

SQLite внутри ядра (`rusqlite`, `bundled`). Файл БД — в `filesDir` приложения, путь передаётся
в ядро при инициализации. Запись отсчётов — транзакциями по пачкам (~1 с данных), чтобы
не терять батарею на fsync. Миграции схемы — внутри ядра (нумерованные SQL-скрипты).

Альтернатива (Room на стороне Kotlin) отвергнута: пришлось бы дублировать хранение при портировании.

## 3. Анализ магнитных аномалий

### 3.1. Физика и источники шума

- Магнитное поле Земли на поверхности ≈ 25–65 мкТл, медленно меняется в пространстве.
  Локальные аномалии: железобетон, трубы, рельсы, автомобили, ЛЭП, крупные металлические
  объекты, геологические структуры.
- Магнитометр телефона: шум ≈ 0.1–1 мкТл, смещение от собственных компонентов (hard iron),
  искажения (soft iron). Android выдаёт калиброванное поле (`TYPE_MAGNETIC_FIELD`) и
  некалиброванное с оценкой смещения (`TYPE_MAGNETIC_FIELD_UNCALIBRATED`). Пишем **оба**.
- Показания в системе координат устройства зависят от ориентации телефона. Поэтому:
  - MVP работает с **модулем вектора |B|** — он от ориентации не зависит;
  - затем, используя `TYPE_ROTATION_VECTOR`, переводим в мировую систему (ENU) и получаем
    вертикальную компоненту и наклонение — более информативные признаки.
- Ложные срабатывания: сам пользователь (ключи, часы, вторая техника), проезжающие машины,
  пересчёт калибровки системой (скачок смещения), низкая точность GNSS.

### 3.2. Пайплайн анализа (в Rust)

1. **Загрузка и очистка**: отбросить отсчёты с `accuracy == UNRELIABLE`, фиксы с
   `h_accuracy > порог` (по умолчанию 25 м), участки без координат.
2. **Геопривязка**: каждому отсчёту датчика — координата линейной интерполяцией между
   соседними фиксами по монотонному времени.
3. **Признаки**: |B|; позже — компоненты в ENU, вертикальная составляющая, градиент
   вдоль трека (d|B|/ds).
4. **Детекция скачков калибровки**: резкие ступени |B| при неизменном некалиброванном
   сигнале → разбить сессию на сегменты с отдельной базовой линией.
5. **Базовая линия**: робастная (медиана + MAD) по сегменту; опционально — ожидаемое поле
   из модели **WMM/IGRF** для широты/долготы/даты (crate `world_magnetic_model` или своя
   реализация), что даёт абсолютную, а не относительную аномалию.
6. **Сетка**: ячейки ~5–10 м (настраиваемо) в локальной проекции (UTM/равнопромежуточной
   вокруг центра сессии). В ячейке: n, медиана, MAD, min/max признака.
7. **Оценка аномальности** ячейки: робастный z-score медианы относительно базовой линии,
   умноженный на функцию доверия от n и точности GNSS. Также помечаем ячейки с высокой
   внутренней дисперсией (нестационарное поле — например, движущийся источник).
8. **Пространственное сглаживание** (опционально): медианный фильтр по соседям, чтобы
   убрать одиночные выбросы.
9. **Результат**: список ячеек (центр, полигон, score, доверие, статистики), трек,
   сводка (базовая линия, число сегментов, доля отброшенных данных), версия алгоритма
   и параметры. Сохраняется как `AnalysisRun`.

### 3.3. Расширяемость на другие сигналы

В ядре — два трейта:

```rust
trait FeatureExtractor { fn extract(&self, session: &Session) -> FeatureSeries; }
trait AnomalyDetector   { fn detect(&self, features: &FeatureSeries, params: &Params) -> GridResult; }
```

Магнитный детектор — первая реализация. Дальше по тому же контракту: Wi-Fi RSSI
(«дыры» и необычно сильные источники), BLE-маячки, уровень сотового сигнала, GNSS
(С/N0, многолучёвость — косвенный признак экранирования), барометр (микрорельеф),
уровень шума. Реестр детекторов отдаёт UI список доступных «слоёв» для карты.

### 3.4. Тестирование алгоритмов

- Синтетические сессии: ровное поле + шум + внедрённый магнитный диполь на известной
  позиции → детектор обязан найти его с заданной точностью. Проверяем и отсутствие
  ложных срабатываний на чистых данных.
- Регрессионные «золотые» дампы с реальных прогулок (хранить в `core/testdata`, небольшие).
- Property-тесты (`proptest`) на инвариантность к ориентации устройства для |B|.
- CLI `sensorium-cli analyze dump.sqlite --out result.geojson` — быстрая итерация без телефона.

## 4. Android-приложение

### 4.1. Стек

- Kotlin 2.x, Jetpack Compose, Material 3, одна Activity, Navigation Compose.
- Архитектура MVVM + однонаправленный поток данных; корутины и Flow.
- DI — Hilt (или ручной, если модулей мало; решить на M1).
- minSdk 26, targetSdk — актуальный (35+).
- Карта — **MapLibre Native Android** с OSM-растровыми или векторными тайлами
  (открытая лицензия, есть встроенные `HeatmapLayer`/`FillLayer`, стиль через JSON).
- Геолокация — платформенный `LocationManager` (GNSS + fused при наличии), без обязательной
  зависимости от Play Services, чтобы собиралось для F-Droid.

### 4.2. Сбор данных

- `RecordingService` — foreground service типа `location` (Android 14+ требует явный тип),
  постоянное уведомление с таймером и кнопкой «Стоп».
- Частоты по умолчанию: магнитометр 50 Гц, акселерометр/вектор вращения 50 Гц,
  гироскоп 50 Гц, GNSS 1 Гц. Используем `maxReportLatencyUs` для батчинга датчиков
  и `WakeLock` PARTIAL на время записи.
- Отсчёты накапливаются в кольцевом буфере и сбрасываются в ядро пачками раз в ~1 с.
- Переживание смерти процесса: ядро коммитит транзакции часто; при рестарте сервиса
  сессия закрывается как «прервана».
- Разрешения: `ACCESS_FINE_LOCATION`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`,
  `POST_NOTIFICATIONS`. `ACCESS_BACKGROUND_LOCATION` не нужен (есть видимое уведомление).

### 4.3. Экраны

1. **Главный / запись**: кнопка Старт/Стоп, живые показания |B| (график последних 30 с),
   статус GNSS (точность, число спутников), счётчик отсчётов, индикатор качества
   калибровки магнитометра с подсказкой «покрутите телефон восьмёркой».
2. **Список сессий**: дата, длительность, длина трека, миниатюра трека, статус анализа.
3. **Сессия**: карта с треком, кнопка «Анализировать», выбор детектора и параметров
   (размер ячейки, чувствительность), экспорт/удаление.
4. **Результат**: тепловая карта + трек, легенда, слайдер порога, тап по ячейке → детали,
   переключение слоёв (разные детекторы), экспорт GeoJSON/CSV/PNG-снимок.
5. **Настройки**: частоты датчиков, единицы, источник тайлов, удаление данных.

### 4.4. Приватность

Все данные остаются на устройстве. Треки GNSS — чувствительные данные: экспорт только по
явному действию пользователя, в настройках — удаление всех данных одной кнопкой. Без
аналитики и сетевых запросов, кроме загрузки тайлов карты (отключаемо, кэш).

## 6. Этапы

### M0 — Скелет (≈ 1 неделя)
- Rust workspace, пустое ядро, UniFFI-функция `version()`.
- Android-проект, Gradle-плагин сборки Rust, вызов `version()` на экране.
- CI зелёный на обеих частях. README с инструкцией сборки.
- **Готово, когда**: свежий клон собирается одной командой и приложение показывает версию ядра.

### M1 — Сбор данных (≈ 2 недели)
- Схема БД и API ядра: `create_session`, `push_samples`, `push_locations`, `finish_session`,
  `list_sessions`, `delete_session`.
- `RecordingService`, разрешения, уведомление, экран записи с живым графиком |B|.
- Список сессий, экран сессии с треком на карте (MapLibre).
- CLI: экспорт сессии в CSV.
- **Готово, когда**: часовая прогулка записывается без потерь и просадки батареи > ~8 %/ч.

### M2 — Магнитный анализ и тепловая карта (≈ 2–3 недели)
- Пайплайн из п. 3.2 (шаги 1–3, 5 относительная базовая линия, 6–9) на |B|.
- Синтетические тесты с диполем, CLI `analyze`.
- Экран результата: тепловая карта, легенда, детали ячейки, порог.
- Экспорт GeoJSON/CSV.
- **Готово, когда**: закопанная/известная металлическая масса на тестовом маршруте
  выделяется на карте, а чистый маршрут — почти не окрашен.

### M3 — Качество измерений (≈ 2–3 недели)
- Детекция скачков калибровки и сегментация (шаг 4).
- Перевод в ENU через вектор вращения; вертикальная компонента, градиент вдоль трека.
- Базовая линия по WMM/IGRF — абсолютные аномалии.
- Фильтр по скорости (в транспорте не считаем), индикатор качества калибровки на записи.
- Сравнение нескольких сессий по одному району (накопление сетки).

### M4 — Расширение на другие сигналы (≈ 3–4 недели)
- Трейты `FeatureExtractor`/`AnomalyDetector`, реестр детекторов, слои на карте.
- Wi-Fi RSSI и BLE-сканы (с учётом троттлинга сканирования в Android), уровень сотового
  сигнала, барометр, GNSS C/N0.
- Общие параметры детекторов в UI, пресеты.

### M5 — Портирование и зрелость (по мере необходимости)
- Swift-биндинги UniFFI, прототип на iOS.
- Десктопное приложение/веб-визуализация результатов CLI.
- Публикация в F-Droid; опционально Google Play.

## 7. Риски

| Риск | Смягчение |
|---|---|
| Калибровка магнитометра Android «прыгает» посреди сессии | Писать и некалиброванный сигнал; сегментация по скачкам; собственная оценка смещения |
| Ориентация телефона маскирует/создаёт аномалии | MVP на \|B\|; далее ENU через вектор вращения; проверка инвариантности тестами |
| Точность GNSS в городе 10–30 м размывает сетку | Ячейки не мельче точности; взвешивание по `h_accuracy`; накопление по нескольким проходам |
| Сам пользователь — источник помех | Подсказки в UI (убрать металл из карманов, держать стабильно); детекция периодичности шагов |
| Сложность сборки Rust ↔ Android отпугнёт контрибьюторов | Gradle-плагин делает всё сам; `rust-toolchain.toml`; инструкция в README; CI как эталон |
| Ограничения фоновых сервисов и батарея | Foreground service, батчинг датчиков, WakeLock только на запись, замеры на M1 |
| Привязка к картографическому SDK | Карта изолирована за интерфейсом `MapRenderer`; данные — нейтральный GeoJSON |

## 8. Решения по умолчанию и открытые вопросы

Принято по умолчанию (можно пересмотреть до начала M1):

1. **FFI — UniFFI**, не ручной JNI и не flutter_rust_bridge.
2. **Хранение в ядре (SQLite/rusqlite)**, Kotlin не держит собственной БД.
3. **Карта — MapLibre + OSM-тайлы**, без Google Maps SDK и Play Services.
4. **Геолокация — платформенный LocationManager**.
